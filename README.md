# simple-boids-like

boidの群れを1つの共有プログラムで操作し、資源収集・拠点防衛などを解いていく
ゲームのアイデアを検証するためのプロトタイプ。

## ゲームの核

- 世界は2次元平面。boidは絶対位置ベクトルと絶対速度ベクトルを持つが、
  **プレイヤーが書く1つのプログラムが全boidを動かす**。
- 1体のboidがアクセスできる情報は「自分の速度」と「視界内(view radius)にいる
  他boid・資源・拠点の、自分を原点とした相対位置・相対速度」だけ。**絶対位置は
  一切わからない。**
- この情報制限のもとで、プレイヤーは意図した創発（boid同士の協調）を起こす
  ようにプログラムを書く必要がある。そこが難易度でありゲーム性の核。
- 将来的にはfactorio / shapez.io / mindustry的な資源収集・基地拡張・研究・
  戦闘を、このboidプログラミングで解いていくことを目指している。

## 現状（Phase 0: アイデア検証プロトタイプ）

「そもそも解けるか」「解く過程が面白いか」を検証する段階。独自言語の設計や
ファイル読み込み実行などは後回しにし、TypeScript + Canvasでホスト言語の関数を
そのまま「boidプログラム」として使う最小構成になっている。

3つの検証シナリオを実装済みで、いずれも複数回のheadless実行・ブラウザ実機の
両方で勝利条件を満たすことを確認済み（詳細は下記シナリオ一覧）。

ロードマップ全体（Phase 0〜4）は元になった計画ファイルを参照:
`~/.claude/plans/boid-1-boid-boid-boid-2-boid-1-boid-boi-soft-puppy.md`

## セットアップ・起動

```sh
npm install
npm run dev
```

表示されるURL（`http://localhost:5173/`）をブラウザで開く。上部のボタンで
3つのシナリオを切り替えられる。

> **WSL2での注意**: `package.json`の`dev`スクリプトは`vite --host`にしてある。
> `--host`を外すとViteが`[::1]`（IPv6ループバック）だけにバインドされ、
> WindowsからWSL2へのポートフォワーディング（IPv4ベース）が届かず
> ブラウザで開けなくなることがある。外さないこと。

## アーキテクチャ

```
src/
  vec2.ts               2Dベクトル演算
  world.ts              World/Boid/ResourceNode/Base の型定義、PHYSICS定数
  perception.ts         boidへの「知覚」の組み立て（絶対座標を相対情報に変換する唯一の境界）
  simulate.ts           1tick分の更新（program呼び出し→物理→採取/搬入/受け渡し）
  render.ts             Canvas描画
  scenario.ts           Scenario共通インターフェース
  scenarios/*.ts         シナリオごとの初期配置・勝利条件
  programs/*.ts          実際に「プレイヤーが書くもの」＝boidプログラム本体
  main.ts                シナリオ切り替えUIとメインループ
```

`perception.ts`が「boidは絶対位置を知らない」という制約をコードレベルで
強制している場所。`World`/`Boid`の絶対座標情報はここから外（program）へは
一切渡らない。

## エンジン仕様

### boidの状態と物理

boidが持つ状態は**位置と速度のみ**（＋内部メモリ・運搬中の資源量・燃料）。
**加速度・慣性の概念は意図的に存在しない。**

- 毎tick、プログラムは「次tickの速度ベクトル」を直接返す
  （`Action.vel`、大きさは`PHYSICS.maxSpeed`でクランプ）
- 次tickの位置は `pos = pos + vel` で決まる（dtによるスケーリングも無し）
- 燃料が0の間は速度を変更できず、直前の速度のまま慣性で進み続ける
  （下記「燃料」参照）

過去に加速度ベースの慣性モデル（`vel += accel * dt`）を実装したことがあるが、
これは意図しない追加仕様だったため撤去済み。**今後もaccel/dt/慣性の類を
勝手に持ち込まないこと。**シンプルさがこのゲームの前提。

### boidプログラムのインターフェース（`src/perception.ts`）

```ts
type Program = (self: SelfView, neighbors: NeighborView[], world: WorldView) => Action;
```

- `SelfView`: 自分のID・速度・運搬中の資源量・残燃料・内部メモリ（読み書き可）。
  **絶対位置は含まれない。**
- `NeighborView[]`: 視界内(`viewRadius`)にいるboid/資源/拠点。相対位置・相対速度
  に加え、boidなら運搬中かどうかと内部メモリ（読み取り専用）も見える。
- `Action`: 次tickの速度ベクトル、および `harvest`(採取) / `drop`(搬入) /
  `handoff`(他boidへの荷物の受け渡し) の意思表示。実際に成立するかは
  `interactRadius`内に対象がいるかをsimulate側で判定する。

### 燃料（fuel）

デフォルトは無制限（`Infinity`）。行動範囲を制限したいシナリオだけ
`createBoid()`で有限の燃料を明示的に渡す（現状は中継リレー輸送シナリオのみ）。
拠点(`interactRadius`内)にいる間だけ全回復する。**距離設定を変えるときは
「片道は燃料内で届くが往復はできない」の関係を崩さないこと**
（超えると誰も資源に到達できず原理的に解けなくなる）。

## シナリオ一覧

| # | シナリオ | 検証していること | 勝利条件 |
|---|---|---|---|
| 1 | 収集・搬入 (`scenarios/gather.ts`) | 最も単純な協調（探索・凝集・運搬）が成立するか | 資源を8個拠点に搬入（45秒相当以内） |
| 2 | 隊列・陣形維持 (`scenarios/formation.ts`) | 局所ルールだけで陣形が自己組織化するか | 拠点周囲の半径35のリング陣形を維持 |
| 3 | 中継リレー輸送 (`scenarios/relay.ts`) | 燃料範囲を超える距離をboid間の手渡しリレーで運べるか | 資源を4個拠点に搬入（90秒相当以内） |

## 開発ルール

### コミット

- **意味のある単位ごとにコミットする**（例: 雛形構築／コアエンジン実装／機能追加／バグ修正、を分ける）。1機能=1コミットが目安で、細かすぎず粗すぎず。
- コミット前に必ず検証する（下記「変更の検証方法」）。動作未確認のままコミットしない。
- コミットメッセージは「何をしたか」より「なぜそうしたか」を書く。
- ユーザーから明示的に頼まれない限りコミットしない（Claude Codeの既定動作）。

### 変更の検証方法

1. **型チェック**: `npx tsc --noEmit`
2. **ビルド**: `npx vite build`（確認後 `dist/` は削除してよい）
3. **ヘッドレス動作検証**（推奨、`npm run dev`より高速に本質的な挙動を確認できる）:
   `tsx`で各シナリオの`createWorld()`→`step()`→`checkWin()`を直接ループさせ、
   実際に勝利条件を満たすか・何ティックかかるかを確認する。乱数要素がある
   シナリオ（formation/relay）は複数回実行して安定性も見ること。
   ブラウザの見た目だけでは気づけない不具合（このプロジェクトで実際に3件
   見つかった: 燃料設計ミス・陣形の振動発散・移動距離が燃料上限を超える設定
   ミス）を洗い出せる。
4. **ブラウザ実機確認**: `npm run dev`で起動し、実際に画面を見る。
   コンソールエラーが出ていないかも確認する。
   （sandbox環境ではheadless chromiumが動かせないことがあるので、その場合は
   ヘッドレス検証で代替し、その旨を正直に報告する。）

## 既知の注意点

- 本プロトタイプは検証目的のため、独自言語・ファイル実行・保存機能などは
  意図的に未実装。
- リレーシナリオの起動時プログラムは「役割分担なしで燃料閾値だけに従う」
  素朴な戦略で、勝利条件は満たすが見た目は「1つの群れが一緒に往復し、
  燃料が減った個体がすれ違いざまに手渡す」キャラバン的な動きになる
  （固定ポストを配置するような、見た目にわかりやすいリレーではない）。
