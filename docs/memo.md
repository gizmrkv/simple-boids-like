# やりたいこと

地形のランダム生成。マインクラフトやfactorioのように。やっぱりランダムな地形、ランダムな資源生成は楽しいから試したい。要検討：アルゴリズムは？世にいっぱいやられているだろうから調査からしてもいいだろう。あとboidが壁や岩などをどのように認識するかとか、パフォーマンスとかも考慮するとかなり考えないといけなさそう。

→ アルゴリズム調査（下記完了済み参照）と、boidに向き(heading)を持たせて
LIDAR的に障害物までの距離を知覚させる、という知覚モデルの方向性までは
決まり、その土台（heading・turn+speed・ローカル座標系）は実装済み
（コミット`491a8ff`）。地形生成・LIDARセンサー自体はまだ未着手。詳細・
残っている論点は[roadmap.md](roadmap.md)の「Phase 0の現状」参照。

## やりたい要素

現状（要コミットid）、広域探索や地形回避はboidどうしの協力が足りない。互いに回避し合うことで効率的に全域を探索する、ぐらいしか相互作用要素がない。
協力しないといけない要素を追加したい。
n体のboidが協力しないと運べない資源。
boidが留まっていないと通れない道。
boidを1~n体犠牲にしないと達成不可能な何かしらの要素。

離れたboidどうしのコミュニケーションをしたい。
ただ無条件でできるとつまらない。
通信網を構築して、通信網にシグナルを流すとそこからつながる全通信網の付近にいるboidが受信できる。
後々、敵という要素を追加したときに自軍の連絡網を破壊されて通信途絶、みたいな状況もできれば面白そう

現状、補給所と資源を置ける場所が同じなっちゃっているが分けたほうがいいかも。
例えば資源置きは基地だけで可能だとすると、boidは資源は都度基地に運ばないといけない。
しかしboidの記憶領域は限られているので帰途を覚えられない。
これがフェロモンを使った誘導アルゴリズム(蟻みたいな)を実装するモチベーションになる。おもしろいかも？
あと補給所も無限に長く広く無制限に建てられるのもつまらなくする要因かもしれない。
無限に広く建てられちゃうと面白みがない気がする。
例えば基地からある程度離れ（仲介する補給所が一定数を超える）と補給所を建てられない、みたいな制約を設けると制約を設けると基地と補給所のエリアの大きさが限られる。
それよりも大きく拡張したいなら基地を立てる必要がある。ただし建設コストが高いので計画的に建てないといけない。そのような難しいロジックを考える必要がある。みたいな。

連絡網という建設物を導入するのではなく、boidが連絡網として機能するのはどうか？
boidが自分が連絡係となると判断したらシグナルが届くギリギリの距離で線上に並び、受け取ったシグナルをそのまま発信、受け取ったらまた発信、これを繰り返して離れたところまでシグナルを届ける、みたいな。

突飛な思いつき。
boidにはスピード、体力、燃料上限、攻撃力、防御力、シグナル発信・受信距離上限みたいなステータスがあって、ポイントを振り分けることでboidがおのおの各ステータスを振り分けることができる。
この振り分け方によって役割分担のモチベーションを自然に導入できそう。
斥候係はスピードと視野を強化、連絡係はシグナル距離を強化、攻撃係は攻撃力を強化、みたいな。
役割分担方法のロジックやその後の動きのプログラムもユーザーは書かないといけない。

敵要素は安易なアイデアだが有望。いくらでも考えられるがぎゃくに自由すぎるので一旦保留。
敵がいないゲームでも面白くなる可能性あるし。

オンライン要素。対戦か、あるいは何かしらのステージのクリア時スコアのボード。ランキング。
他要素と競合しなさそうだし後回しで良さそう。

# 考えたいこと

現状（最新のコミットIDを付記して記録しておきたい）、boidはcargoがない状態で資源に触れると勝手に資源を取得して、資源を持っている状態で基地または補給所に触れると勝手に置いちゃう。
もしも、いずれ回収及び提出を制御したくなったらこの挙動を変える必要あり。特に勝手に拾っちゃうのは致命的かつユーザーにかなり面倒な実装を求めることになりそう。
雑な提案：boidに、もしも~~に触れたら勝手に回収するホワイトリスト変数と、勝手に基地または補給所に提出してよいかを制御するフラグ変数をもたせてこれを任意のステップで制御可能にする。
要検討：今後boidにどんな制御要素を追加していくかわからない状況でこれに決めてしまっても良いものか？保留にしたほうが良いか？


# 完了済み

- 広域探索（フェロモンなし版）を`scenarios/frontier.ts`として試作した
  （コミット`913458a`、その後`7a07d32`でv2として書き直し）。既存シナリオが全て使って
  いた「資源はこの方向にある」という決め打ち(`EXPLORE_DIR`)を廃した。
  v1は各boidに個体固有の固定探索方位（`memory[3]`、spawn時に均等分散）を
  割り当てて放射状に分散させる方式でheadless 10回中7勝だったが、ユーザーから
  「方向はboid自身に周囲を見て判断させたい、初期位置も拠点付近でランダムに
  したい」という要望を受けてv2に書き直した。v2はReynoldsのboidsアルゴリズム
  の分離則（Separation、視界内の他boidから離れる方向へ操舵）だけで拡散を
  自己組織化させる方式。v2の初期実装ではheadless 10回中3〜4回で**全boidが
  燃料切れのまま動けなくなる**不具合（拠点は見えているが密集による分離力で
  ピンポイントの`interactRadius`にたどり着けず孤立するデッドロック）が
  見つかり、`relay.ts`と同じ`lowFuel`パターン（低燃料時は分離力を無視して
  アンカーへ直進）を追加して解消。修正後はheadless **10回中10勝**（v1の
  7/10より改善）。
  → 上記の問い「補給所を随所に建てるならフェロモンの意義は薄いのでは」への
  現時点の答え：**この設定（拠点付近ランダムスポーン・WIN_AMOUNT=5）では、
  フェロモンなし・分離則による自己組織化的な拡散だけで十分機能する**。より
  厳しい条件（資源をさらに遠く・狭くする、スポーンをフィールド全体に広げる
  等）でも同じ結論が成り立つかは未検証。詳細は[docs/roadmap.md](roadmap.md)
  参照。
- 資源クラスタを1箇所から4箇所に増やした（コミット`59052e9`）。headless
  10回中10勝を維持したまま、勝利までのtickが653〜3941から542〜1431へ短縮。
- 呼称を「資源パッチ」から「資源クラスタ」に変更した。ユーザーの好みにより
  （「クラスタ」の方が「ソフトウェアの修正パッチ」に紛れず意味がストレートに
  伝わる、という理由。もともとコード内では`clusterCenter`という変数名を
  自然に使っていた経緯もある）。
- boidの視界範囲(`PHYSICS.viewRadius`)をcanvas上に描画するデバッグ表示と、
  GUIでのON/OFF切り替えチェックボックスを追加した（コミット`651198b`）。
  `render()`に`showViewRadius`引数を追加し、trueのときboidごとに視界半径の
  円をストロークのみ（塗りつぶしなし、シアン系の低アルファ色）で描画する。
  チェックボックスは`main.ts`のシナリオ切り替え・リセット処理
  (`renderButtons()`が`#controls`を毎回全消去・再構築する)をまたいで
  表示状態が消えないよう、モジュールスコープで一度だけ生成したDOMノードを
  `appendChild`で再アタッチする方式にした（チェックボックス自体が状態を
  保持するので、別途状態変数は持たない）。
- 資源の保管を拠点/補給所ごとの個別管理からグローバル管理（`World.stored`
  単一カウンタ）に変更した（コミット`ea6cd38`）。`Base`/`Station`から
  それぞれの`stored`フィールドを削除し、`simulate.ts`のdrop処理は
  `world.stored`に直接加算する。4シナリオ(gather/relay/supply-line/
  frontier)のcheckWinは`world.bases.reduce(...)`等の合算をやめ
  `world.stored`を直接参照するよう変更。事前調査でどのboidプログラムも
  拠点/補給所の`amount`（≒旧`stored`）を読んでいなかったため
  （`relPos`による位置ベースの判断のみ）、`perception.ts`の
  `NeighborView`から拠点/補給所の`amount`を削除しても挙動には影響しない
  ことを確認済み。canvas上の拠点/補給所ごとの個別数値表示（`fillText`）も
  削除し、合計は既存のステータス表示（`checkWin().detail`）のみで見える
  ようにした。ヘッドレス検証で変更前と同等の勝率・勝利tick数を確認。
- 地形のランダム生成アルゴリズムを比較調査した（`research/20260811-terrain-generation-algorithms/`、
  コミット`03838ae`）。ノイズ/セルオートマトン/ポアソン円盤/WFC/Voronoiの
  比較表、リソース配置手法、視界制限下エージェントの障害物回避に関する
  既存研究をdeep-researchスキルで調査。
- boidにheading(向き)を導入し、行動を`vel`ベクトル直接指定から
  `turn`(回転角)+`speed`(速さ)の2スカラーに、知覚全体(資源・拠点・他boid)を
  heading基準のローカル座標系に刷新した（コミット`491a8ff`）。上記の
  アルゴリズム調査から、「boidに向きを持たせ、現実のロボットのLIDARのように
  前方の障害物までの距離を知覚させる」という設計に議論が発展した結果の
  土台整備（地形生成・LIDARセンサー自体はまだ未着手）。旋回に1tickあたりの
  上限は設けていない（無制限なら旧`vel`直接指定モデルと数学的に等価な
  表現力で、操作難易度を上げる制約を無断で追加しないため）。この移行に
  伴い、全boid共有の固定探索方向`EXPLORE_DIR`に依存していた
  `relay.ts`/`ladder.ts`/`supply-line.ts`の3シナリオを削除した（Station建設・
  リーダー選出パターンは`frontier.ts`が引き続き使うため存続）。詳細・
  残っている論点（LIDARのレイ本数・視野角、地形生成アルゴリズムの選定等）は
  [roadmap.md](roadmap.md)参照。
