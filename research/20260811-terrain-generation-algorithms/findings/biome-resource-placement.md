# バイオーム的配置によるリソース配置手法

調査目的: TypeScript + Canvas 2D の軽量2Dシミュレーション（boidベースのマルチエージェントゲーム）に、
地形（高さ・湿度・地形タイプ）とリソース（鉱石・木材など）を関連付けた配置手法を導入すべきか判断する
ための一次情報収集。

## 1. 複数ノイズレイヤーからバイオームを決定する手法

### 1.1 基本パターン：独立したノイズ2枚 + 閾値/ルックアップテーブル

Red Blob Games の解説記事が最も実装が簡単で参照価値が高い一次情報。

- 標高 (elevation) と湿度 (moisture) を**別々のシード**で生成した2枚のノイズマップとして独立に計算する
  （シードを変えられないライブラリの場合は `noise(nx + 1000, ny)` のようにオフセットをずらして代用）。
- 各セルで `(elevation, moisture)` の組を求め、階層的な `if` 分岐（または2次元ルックアップテーブル）で
  バイオームを決定する。例:
  ```
  if (e < 0.1) return OCEAN;
  if (e < 0.12) return BEACH;
  if (e > 0.8) {
    if (m < 0.1) return SCORCHED;
    ...
  }
  ```
  標高を主要カテゴリとして先に分岐させ、その中を湿度で細分化するのが典型。
- Whittaker biome diagram（生態学における年間気温×年間降水量でバイオームを分類する古典的な図）を
  離散化してこのルックアップテーブルの元ネタにする、という手法が複数の解説記事・学術論文
  （AutoBiomes論文）で言及されている。16分類（温度4段階×湿度4段階）程度が典型例。
- 記事は「it's fast」「simple」と明言しており、各セルの計算が他セルに依存しない局所計算のため
  並列化・無限マップ生成にも向くとしている。ただし具体的なFPS/msのベンチマーク数値は無い。

出典: [Red Blob Games: Making maps with noise functions](https://www.redblobgames.com/maps/terrain-from-noise/),
[AutoBiomes: procedural generation of multi-biome landscapes (Springer)](https://link.springer.com/article/10.1007/s00371-020-01920-7)

### 1.2 Minecraft方式：多層ノイズ + クロスフェード（3Dだが考え方は流用可）

Minecraft（1.18以降のCaves & Cliffs地形生成）は温度・湿度・侵食度(erosion)・
連続性(continentalness)・奇妙さ(weirdness)という**5種類以上のノイズパラメータ**を組み合わせて
バイオームを決定する。生成は大きく2段階：

1. **Generation フェーズ**: ベース地形とバイオーム割り当てを作る
2. **Population フェーズ**: 木・鉱石・構造物などのフィーチャーを配置する

これは「地形決定 → バイオーム決定 → その上にリソースを配置」という、まさに本調査が探している
2段階パイプラインの実例。

また、旧来のクラシックなMinecraft地形生成では、3つの独立ノイズ（上限境界ノイズ・下限境界ノイズ・
メインノイズ）を組み合わせ、メインノイズで上限/下限の間をクロスフェードすることで
「なめらかな変化がところどころ急激に途切れる」効果を出している。パフォーマンス面では、
ノイズ計算コストを抑えるために**低解像度で density グリッドを計算してから補間で拡大する**
サブサンプリング手法が使われている（層を増やすほど計算コストが線形に増えるため、そのまま
全セルで計算せず間引く、という対策が実例として存在する）。

出典: [Minecraft Wiki: World generation](https://minecraft.wiki/w/World_generation),
[Terrain generation in Minecraft (nornagon)](https://blog.nornagon.net/terrain-generation-in-minecraft/),
[The World Generation of Minecraft - Alan Zucconi](https://www.alanzucconi.com/2022/06/05/minecraft-world-generation/)

## 2. バイオーム決定後のリソース配置手法

### 2.1 密度関数・ノイズによる濃淡（Minecraftの鉱脈=ore vein）

Minecraft 1.18+ の鉱脈生成は3つのノイズ関数の組み合わせ：

- **toggle**: 指定Y範囲外では常に0。範囲内では正負の値を取り、正負で「鉄の鉱脈」か「銅の鉱脈」かを
  切り替える。
- **ridge**: 範囲外では常に-0.08固定。0より大きければそのブロックの生成をスキップ（＝鉱脈の輪郭を
  ridge状のノイズで削る）。
- **gap**: 鉱脈内での「鉱石:充填材」の比率を10%〜30%の範囲で決める。

さらにY座標ごとに「三角分布 (triangle distribution)」を採用しており、各鉱石はピークとなる深さを
持ち、そこから上下に離れるほど出現率が線形に減衰する（例: ダイヤ/レッドストーンはY=-59が
ピーク、鉄は山岳部Y=232に大きな鉱脈が出る）。これは「バイオーム/地形パラメータ→密度関数→
配置確率」という設計の典型例。

出典: [Minecraft Wiki: World generation](https://minecraft.wiki/w/World_generation),
[Noise router – Minecraft Wiki](https://minecraft.wiki/w/Noise_router)

### 2.2 Factorio方式：spot noise（円錐状パッチ + 適合性ノイズ）

Factorioの資源パッチ配置アルゴリズム（0.17以降、noise expressionsとして再実装）は以下の流れ:

1. マップを一定サイズの領域(region)に分割する。
2. 各領域内にランダムな候補点を複数生成する。
3. 各候補点についてノイズ式から「密度・数量・半径・適合性(candidate spot quality)」を算出する。
4. 適合性順にソートし、目標総量に達するまで上位の点を採用する。
5. 各パッチは「円錐（中心が濃く、外周が薄い）」形状で生成され、さらに基礎ノイズを加算して
   きれいな円形を崩す。

地形との連動例として、傾斜(slope)を適合性スコアに反映させることで水中や崖に資源が
配置されないようにしている、という記述がある（水位が上がると配置も追従して動く）。
開発者ブログではパフォーマンスに関する定量的な言及はなかった。

出典: [Friday Facts #258 - New autoplace](https://factorio.com/blog/post/fff-258),
[factorio-data: resource-autoplace.lua](https://github.com/wube/factorio-data/blob/master/core/lualib/resource-autoplace.lua)

### 2.3 ポアソン円盤サンプリングとの組み合わせ（植生・オブジェクト散布）

木や岩などの離散オブジェクトを「自然に見える密度」で撒く手法としてPoisson disk samplingが
広く使われている。特徴:

- 最小距離パラメータ`r`を設定し、既存の点から`r`未満の位置には新しい点を置かない → 密集しすぎず
  かつ規則的すぎない「有機的」な分布になる。
- 複数の物体クラス（例: オーク、松、茂み）ごとに異なる最小距離を設定し、クラス間距離も個別に
  設定可能（松同士は3m、松と茂みは1.5m、など）。
- バイオーム/密度マップとの組み合わせ方としては、ノイズ値やバイオーム種別によって
  「その領域でのポアソン円盤サンプリングの半径`r`（＝密度）」や「採用確率」を変調する、という
  応用が一般的に紹介されている（密度が高いバイオームほど`r`を小さくする、等）。
- No Man's SkyやThe Witcher 3が環境ディテール配置にPoisson的分布を使っているとされる（一次情報の
  直接引用ではなく解説記事の紹介レベル）。

出典: [Game Dev Mechanics: Poisson Disk Sampling — How It Works](https://moonjump.com/game-dev-mechanics-poisson-disk-sampling-how-it-works/),
[Poisson Disc Sampling (gameidea.org)](https://gameidea.org/2023/12/27/poisson-disk-sampling/)

## 3. 実装コスト・パフォーマンス特性

- ノイズレイヤーを1枚追加するごとに、少なくとも「セルごとに1回のノイズ関数呼び出し」が線形に
  増える。Red Blob Gamesの記事はこれを「fast」「simple」と表現しているが定量値の記載はない。
- Minecraft側の実例では、密度計算のコストを抑えるために**低解像度で計算してから補間で拡大**する
  最適化が行われている（全セルでフルノイズ評価をしない）。層を増やすほど計算コストが増える問題への
  現実的な対策として参考になる。
- 2D Canvasベースの軽量実装であれば、静的な地形生成時（ワールド生成時に1回だけ）にバイオーム判定と
  リソース配置を行い、実行時（tick処理）では再計算しない設計にすればランタイムコストへの影響はほぼ
  ゼロにできる。これは今回の一次情報からの直接引用ではなく、収集した情報を踏まえた設計的示唆。
- FactorioのSpot noiseやMinecraftのore veinのような「領域分割 + 候補点 + 適合性スコアでソート」
  方式は、単純な閾値ルックアップテーブルより実装コストが高い（候補点生成・ソート・選択のロジックが
  追加で必要）。閾値/ルックアップテーブル方式（Red Blob Games流）の方が実装コストは低い。

## 4. 「地形と資源を関連付けること」自体のゲームデザイン上のトレードオフ

### 4.1 予測可能性の利点（プレイヤー/エージェント視点）

- Minecraftの例では、プレイヤーは経験則で「この深さ・この地形ならこの資源」という予測を立てて
  行動できる（ダイヤは深い場所、鉄は山岳部、など）。これはエージェント（boid的な自律プログラム）
  が「視界内の地形情報から資源の存在確率を推定する」戦略を組めることを意味し、本プロジェクトの
  「相対情報のみで意思決定する」制約と相性が良い可能性がある。

### 4.2 単調・予測可能すぎるという批判

- Little Martianのブログ記事は、Perlin/Simplexノイズベースの手続き生成が「ユニークだが退屈」な
  世界になりやすい問題を指摘している。理由は「人間の脳はパターン認識に長けており、生成アルゴリズムが
  疑似ランダムかつ限られたアセットの組み合わせしか使わない場合、プレイヤーはすぐパターンを学習して
  しまい、探索の魔法が失われる」というもの。
- 同記事が挙げていた対策（本プロジェクトへの応用可能性を含め記録）:
  1. 同じバイオームでも配置するオブジェクトの種類・密度を大きく変えて視覚的多様性を出す
  2. 温度・湿度・標高の基本ノイズに加え、特殊バイオーム専用の追加ノイズを重ねて通常バイオームを
     局所的に上書きする
  3. 複数のノイズ値を非線形に変換・合成し、「長く連なる鉱脈帯」のような意図的なパターンを作る
  4. 変化速度の異なる複数の温度ノイズを合成し、急激な変化を抑えつつ局所差は残す
  5. （面白い逆転例）鉱脈バイオームが周囲の標高を押し上げるなど、リソース配置が地形に**逆に**
     影響を与えるフィードバックを入れることで、同じ特徴の単純な反復を崩す
- 一般的な考察として、「デザイナーがアルゴリズムを制御すればするほど、結果は予測可能で無難になり、
  行き過ぎると手作業でレベルを作るのと大差なくなる」というパラドックスがゲームデザイン系の記事で
  複数回言及されている（GameDeveloper.comの記事など）。

出典: [Making Procedural World Gen Interesting - Little Martian](https://little-martian.dev/21-03-19-interesting-world-gen/),
[Procedural Generation: By Molecule or Mythology (Game Developer)](https://www.gamedeveloper.com/design/procedural-generation-by-molecule-or-mythology)

### 4.3 本プロジェクトへの示唆（判断材料であり結論ではない）

- 「地形→バイオーム→リソース」の2段階パイプライン自体は実装コストが低く（特にRed Blob Games流の
  閾値テーブル方式）、boidエージェントに「地形情報から資源の存在確率を推測する」という新しい知覚・
  戦略の余地を与えられる。これは既存の「視界内の相対位置のみ知覚可能」という設計制約と両立しうる。
- 一方で、決定論的すぎる配置は探索の面白さを削ぐ可能性がある、という指摘が複数の情報源で
  一致している。対策として「ノイズによる密度濃淡」「局所的な例外バイオーム」「軽いランダム性の
  上乗せ（ポアソン円盤等）」を組み合わせる設計が一般的。

## 5. 限界・未解決事項

- Factorioのspot noiseアルゴリズムの内部実装（`resource-autoplace.lua`）はソースコードの存在は
  確認できたが、中身の詳細読解までは今回行っていない。
- パフォーマンスの定量的なベンチマーク（「レイヤーN枚でXms」等の具体的数値）は、調査した一次情報
  （Red Blob Games、Factorio FFF、Minecraft Wiki）のいずれにも見当たらなかった。これは今回の
  調査で「該当する一次情報なし」と判定した項目。
- 「地形と資源の関連付けの是非」について、学術的・定量的なプレイテスト結果（A/B比較など）を伴う
  一次情報は見つからなかった。Little Martian記事は開発者の個人的な考察であり、査読済み研究では
  ない点に注意。
- AutoBiomes論文（Springer/ResearchGate）は要旨レベルの情報しか確認しておらず、詳細な数式・
  アルゴリズムまでは踏み込めていない。
